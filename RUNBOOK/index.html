    ZenithNMS — 운영 런북¶

    배포 후 상태 확인, 로그 조회, 장애 대응, 백업/복구 절차를 정리한 문서입니다. 사용자 화면에서 보이는 증상별 해결법은 앱 내 "사용자 매뉴얼" → 16. 장애 진단에 별도로 있고, 여기서는 그보다 한 단계 아래(인프라/운영자 관점)를 다룹니다.

    1. 상태 확인¶

    sudo docker compose ps

    세 컨테이너(zenith_postgres, zenith_backend, zenith_frontend) 모두 Up이어야 하고, postgres/backend는 (healthy)까지 떠야 정상입니다.

    ⚠️ backend의 healthcheck(GET /api/health)는 프로세스 생존만 확인하고 DB 연결은 확인하지 않습니다. 즉 postgres가 실제로 응답 불가 상태여도 backend 컨테이너는 (healthy)로 보일 수 있습니다 — DB 문제가 의심되면 아래 4. DB 장애를 함께 확인하세요.

    2. 로그 확인¶

    sudo docker compose logs -f backend      # 실시간
sudo docker compose logs backend --since 1h
sudo docker compose logs postgres
sudo docker compose logs frontend

    로그는 별도 파일로 저장되지 않고 컨테이너 stdout(uvicorn 로그)에만 남습니다. 컨테이너를 down 하면 기본 docker 로그 드라이버 설정에 따라 사라질 수 있으므로, 장애 조사 중이라면 먼저 로그를 파일로 백업해두세요.

    sudo docker compose logs backend > backend_$(date +%Y%m%d_%H%M).log

    증상별(인터페이스 데이터 없음, CPU/메모리 이상, 폴링 안 됨 등) 세부 로그 grep 패턴은 사용자 매뉴얼 16장에 정리되어 있습니다.

    3. 데이터 보존(retention) — 자동화되어 있지 않음¶

    ⚠️ RAW_RETENTION_DAYS(7일) / HOURLY_RETENTION_DAYS(30일) / DAILY_RETENTION_DAYS(365일) 설정값은 config.py에 존재하지만, 이를 정리하는 크론/스케줄러가 없을 뿐 아니라 이 설정값 자체가 실제로는 쓰이지 않습니다. DELETE /api/metrics/retention은 SQL 함수 cleanup_old_metrics()(backend/migrations/init.sql)를 호출하는데, 이 함수는 7일/30일/365일을 SQL에 직접 하드코딩하고 있어 위 설정값을 바꿔도 아무 효과가 없습니다. 정리는 아래 API를 수동(또는 직접 만든 cron)으로 호출해야만 실행됩니다.

    curl -X DELETE http://localhost:3000/api/metrics/retention \
  -H "Authorization: Bearer <로그인으로 받은 JWT>"

    이 엔드포인트를 포함해 /api/auth/me를 제외한 모든 API가 인증을 요구합니다(자세한 내용은 6. 포트 & 보안 유의사항 참고) — 토큰 없이 호출하면 401이 반환됩니다.

    이걸 방치하면 metrics_raw가 주 단위 파티션으로 쌓이기만 하고 오래된 파티션이 드롭되지 않아 디스크가 계속 증가합니다. 운영 중이라면 이 호출을 매일/매주 실행하는 cron을 별도로 구성하는 것을 권장합니다.

    4. DB 장애¶

    증상: backend는 떠 있는데 대시보드/장비 목록이 전부 비거나 500 에러.

    sudo docker compose ps postgres                     # Up (healthy)인지 확인
sudo docker compose logs postgres --tail 100
sudo docker compose exec postgres pg_isready -U zenith -d zenithnms

    postgres가 죽어 있으면 sudo docker compose up -d postgres로 재기동하세요. backend의 DB 엔진은 pool_pre_ping=True로 설정되어 있어(backend/app/database.py) 커넥션 풀이 끊긴 연결을 자동으로 감지하고 재연결하므로, 일반적으로는 backend를 재시작할 필요가 없습니다. postgres 복구 후에도 계속 에러가 난다면 그때 sudo docker compose restart backend를 시도하세요.

    5. 백업 & 복구¶

    DB는 named volume(pg_data) 하나에만 저장됩니다. 별도 자동 백업은 구성되어 있지 않으므로, 스키마 변경 배포 전에는 반드시 수동 백업하세요.

    백업 (--clean --if-exists로 떠야 복구 시 기존 스키마와 충돌 없이 DROP 후 재생성됨) 

    sudo docker compose exec -T postgres pg_dump -U zenith -d zenithnms --clean --if-exists > backup_$(date +%Y%m%d).sql

    복구 (같은 이름의 DB로 덮어쓰기) 

    cat backup_20260831.sql | sudo docker compose exec -T postgres psql -U zenith -d zenithnms -v ON_ERROR_STOP=1

    ⚠️ --clean 없이 뜬 백업을 이미 스키마가 존재하는 DB(예: init.sql로 새로 만든 컨테이너)에 그대로 복구하면 CREATE TABLE 등이 전부 "already exists" 에러로 실패하는데, -v ON_ERROR_STOP=1 없이는 psql이 에러를 무시하고 계속 진행해 일부만 복구된 상태를 성공한 것처럼 보이게 됩니다. 반드시 위 두 옵션을 함께 사용하세요.

    볼륨 전체 백업 (DB 파일 자체를 통째로 — pg_dump보다 빠르지만 postgres를 반드시 멈추고 떠야 함)

    ⚠️ postgres 컨테이너가 떠 있는 상태로 데이터 파일을 그대로 tar로 뜨면 쓰기 도중인 파일이 섞여 들어가 복구 시 깨지거나 실패할 수 있습니다. 평소 백업은 위 pg_dump 방식을 쓰고, 이 방법은 컨테이너를 멈춘 뒤에만 사용하세요.

    sudo docker compose stop postgres
sudo docker run --rm -v zenithnms_pg_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/pg_data_$(date +%Y%m%d).tar.gz -C /data .
sudo docker compose start postgres

    6. 포트 & 보안 유의사항¶

    포트 노출 범위 참고
    3000 (Nginx/Frontend) 호스트 전체 정상적인 진입점
    5432 (PostgreSQL) 호스트 전체 docker-compose.yml에 계정(zenith/zenith)이 하드코딩되어 있음 — 외부 네트워크에 노출된 서버라면 방화벽으로 5432를 반드시 차단할 것
    8000 (Backend) 컨테이너 내부만 호스트에 직접 노출 안 됨, 정상
    • JWT_SECRET_KEY가 기본값(change-me-in-production)인 채로 운영 중이면 즉시 auth.env에서 변경. 기본값을 쓰면 코드를 아는 누구나 유효한 토큰을 위조할 수 있습니다.
    • ✅ (2026-09-01 수정 완료) /api/auth/me를 제외한 모든 API(devices/metrics/alerts/topology/mib/geo/processes/manual 등)에 인증이 걸려 있지 않던 문제가 있었으나, 각 라우터에 dependencies=[Depends(get_current_user)]를 추가해 현재는 로그인 없이 API를 호출할 수 없습니다. /api/health는 Docker healthcheck 때문에 의도적으로 인증 없이 열어둔 상태입니다.
