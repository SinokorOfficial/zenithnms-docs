    1. 시스템 개요¶

    주요 기능¶

    메뉴 기능
    대시보드 전체 장비 상태 현황, 활성 알람 요약, 장비별 CPU/메모리 패널
    장비 목록 SNMP 장비 등록·수정·삭제, 4탭 상세 데이터 조회, 프로세스 모니터
    장애 예측 선형회귀 기반 CPU/메모리 추세 예측, Z-score 이상 탐지
    토폴로지 맵 LLDP/CDP 기반 네트워크 자동 탐색 및 6가지 스타일 시각화
    알람 센터 임계값 기반 알람 조회·확인·해결, 임계치/이메일 알림 설정
    MIB Browser MIB 파일 파싱, SNMP Walk/GET 테스트, SNMP 진단
    사용자 매뉴얼 바로 이 문서(docs/manual.md)를 앱 안에서 실시간 렌더링. 예전에 별도였던 "관리자 매뉴얼" 메뉴는 이 문서로 통합됨 (2026-08-28)

    기술 스택¶

    구성 요소 기술
    백엔드 Python 3.10 (Docker 이미지 기준) / FastAPI / asyncpg
    폴링 엔진 pysnmp-lextudio (비동기 SNMP)
    데이터베이스 PostgreSQL 16 (주 단위 파티션 테이블 기반 시계열)
    프런트엔드 React 18 / TypeScript / Tailwind CSS / react-markdown
    인증 JWT 액세스 토큰 + SMS(CoolSMS) OTP, 실패 시 이메일 폴백
    인프라 Docker Compose / Nginx (프런트 정적 서빙 + /api 리버스 프록시)

    수집 데이터¶

    • 시스템 정보: sysDescr, sysName, sysUptime, sysLocation, sysContact
    • 인터페이스: IF-MIB 전체 (ifName, ifDescr, ifAlias, ifSpeed, ifHighSpeed, OperStatus, 64비트 카운터)
    • CPU/메모리: 장비 벤더를 자동 감지해 벤더 전용 OID를 먼저 시도하고, 실패하면 범용 MIB로 순차 폴백 (자세한 내용은 14장 참고)
    • 프로토콜 통계: Ping RTT/손실, ICMP/TCP/UDP MIB-II 카운터
    • 프로세스: HOST-RESOURCES-MIB hrSWRunTable (지원 장비에 한함, DB 미저장·실시간 조회)

    2. 로그인 및 인증¶

    ZenithNMS는 단일 관리자 계정 + 2단계 인증(OTP) 구조입니다. 회원가입/다중 사용자 개념은 없습니다.

    로그인 절차¶

    1. 이메일/비밀번호 입력 → POST /api/auth/login
    2. 자격 증명이 맞으면 서버가 6자리 OTP를 생성해 등록된 휴대폰 번호로 SMS 발송 (AUTH_USER_PHONE 환경변수)
    3. 화면에 마스킹된 번호(예: 010-****-2823)로 발송 완료 안내
    4. OTP 입력 → POST /api/auth/verify-otp → 검증 성공 시 JWT 액세스 토큰 발급
    5. 이후 요청은 Authorization: Bearer <token> 헤더로 인증

    OTP 특성¶

    항목 내용
    유효 시간 5분 (300초)
    저장 방식 백엔드 프로세스 in-memory(재시작 시 초기화) — 그래서 uvicorn --workers 1 고정 필요
    SMS 발송 CoolSMS API (HMAC-SHA256 서명)
    SMS 자격증명 미설정 시 이메일(SMTP)로 OTP 폴백 발송, 그래도 실패하면 백엔드 로그에 평문 OTP 기록
    SMS/이메일 자격증명은 auth.env에 보관하며 절대 git에 커밋하지 않습니다.

    비밀번호 찾기 (이메일 재설정 링크)¶

    로그인 화면 하단의 "비밀번호를 잊으셨습니까?" 를 누르면 비밀번호 찾기 화면으로 전환됩니다.

    1. 등록된 관리자 이메일(AUTH_USER_EMAIL)을 입력 → POST /api/auth/forgot-password
    2. 이메일이 등록된 계정과 일치하면 그 주소로 재설정 링크가 담긴 메일이 발송됩니다 (계정 존재 여부를 노출하지 않기 위해 화면 안내 문구는 일치 여부와 무관하게 동일)
    3. 메일의 비밀번호 재설정 버튼(또는 /reset-password?token=... 링크)을 열어 새 비밀번호를 두 번 입력 → POST /api/auth/reset-password
    4. 변경 완료 후 로그인 화면으로 이동, 새 비밀번호 + OTP로 로그인
    항목 내용
    링크 유효 시간 30분, 1회용 (PASSWORD_RESET_TTL_MINUTES로 조정)
    재요청 제한 재설정 메일은 1분에 1회만 발송
    비밀번호 정책 8자 이상, 영문 + 숫자 포함
    저장 위치 새 해시는 DB auth_credentials 테이블(id=1)에 저장되며 auth.env의 AUTH_USER_PASSWORD_HASH보다 우선 적용됨. 따라서 재설정 후 컨테이너 재생성 없이 즉시 반영되고, auth.env는 초기값 역할만 함
    링크 주소 브라우저 요청의 Origin(예: http://localhost:3000)을 기준으로 생성, 없으면 APP_BASE_URL 환경변수 사용
    메일 발송 알림 메일과 같은 SMTP 설정(SMTP_HOST/USER/PASSWORD) 사용. SMTP 미설정 시 발송 불가 안내가 뜨고 백엔드 로그에 링크가 기록됨
    DB에 저장된 해시를 지우고 auth.env 값으로 되돌리려면 UPDATE auth_credentials SET password_hash = NULL WHERE id = 1; 을 실행하면 됩니다.

    3. 시작 및 종료¶

    최초 실행 (빌드 포함)¶

    cd ~/projects/zenithnms
sudo docker compose down
sudo docker compose build --no-cache
sudo docker compose up -d

    일반 시작¶

    cd ~/projects/zenithnms
sudo docker compose up -d

    특정 서비스만 재빌드¶

    sudo docker compose up -d --build backend    # 백엔드만
sudo docker compose up -d --build frontend   # 프런트엔드만 (npm run build 필요 없음, Dockerfile이 처리)

    상태 확인¶

    sudo docker compose ps

    정상 상태: 

    NAME               STATUS
zenith_postgres    Up (healthy)
zenith_backend     Up (healthy)
zenith_frontend    Up

    로그 확인¶

    sudo docker compose logs -f               # 전체 로그
sudo docker compose logs -f backend       # 백엔드 (폴링 엔진 포함)
sudo docker compose logs -f frontend      # 프런트엔드 (nginx 로그)

    종료¶

    sudo docker compose down

    4. 접속 방법¶

    항목 주소 비고
    웹 앱 http://localhost:3000 React SPA (nginx가 정적 파일 서빙)
    API (프록시 경유) http://localhost:3000/api/... nginx가 /api/를 백엔드(8000)로 그대로 전달
    Swagger UI 현재 미노출 FastAPI 기본 /docs는 /api 프리픽스가 아니라서 nginx 프록시로는 접근 불가. 필요 시 docker compose exec backend 또는 백엔드 포트를 직접 호스트에 노출해야 함
    PostgreSQL localhost:5432 (user: zenith / pw: zenith / db: zenithnms) docker-compose에 직접 포트 매핑됨
    백엔드 컨테이너 자체는 docker-compose상 호스트에 포트가 노출돼 있지 않습니다 — 반드시 3000번 포트(nginx 프록시)를 통해서만 API에 접근합니다.

    5. 대시보드¶

    앱 실행 시 첫 화면. 전체 현황을 한눈에 표시합니다. 60초(폴링 주기)마다 자동 갱신됩니다.

    표시 항목¶

    항목 설명
    장비 현황 카드 전체 / UP / DOWN 장비 수 및 가용률
    알람 현황 카드 활성 / Critical / Warning 알람 수
    장비 상태 그리드 등록된 전체 장비 상태 카드 (Grid/Table 뷰 전환)
    장비별 CPU/메모리 패널 유형·제조사 필터, 정렬, 임계치 설정(localStorage), 6시간 히스토리 차트

    장비별 CPU/메모리 패널 상세¶

    항목 설명
    장비 유형 필터 서버·라우터·스위치·방화벽·AP 등
    제조사 필터 유형 선택 후 해당 유형의 벤더로 2단계 필터
    정렬 CPU+메모리 합산 / CPU 사용률 / 메모리 사용률 기준 오름차순·내림차순
    임계치 설정 전체 공통 + 제조사별 독립 설정, 브라우저 localStorage에 영구 저장
    임계치 초과 표시 설정값 초과 시 해당 장비 카드가 주황색으로 깜빡임
    대시보드 패널의 임계치 설정은 알람 센터에 해당 장비의 벤더/모델(또는 장비 지정) 임계치가 없을 때만 적용됩니다. 우선순위는 11장을 참고하세요.

    8. 프로세스 모니터¶

    장비 상세 패널의 자원 탭 하단에 표시됩니다. HOST-RESOURCES-MIB의 hrSWRunTable/hrSWRunPerfTable을 실시간으로 수집하며 DB에는 저장하지 않고 화면을 열 때마다 즉시 SNMP로 조회합니다.

    컬럼¶

    컬럼 출처 OID (HOST-RESOURCES-MIB) 설명
    PID hrSWRunIndex .25.4.2.1.1 프로세스 인덱스
    Command hrSWRunName .25.4.2.1.2 프로세스 이름
    CPU% hrSWRunPerfCPU .25.5.1.1.1 두 폴링 간 centiseconds 델타 ÷ 경과초
    Memory / PSS hrSWRunPerfMem .25.5.1.1.2 메모리 사용량 (KB → MB/GB 자동 변환). PSS는 표준 SNMP에서는 이 값과 동일하게 표시
    State hrSWRunStatus .25.4.2.1.7 running / runnable / notRunnable / invalid

    사용법¶

    • 프로세스 테이블 행 클릭 → 상단 CPU% 라인 차트에 추가/제거 (최대 6개 동시 추적)
    • 15초 자동 갱신 (우측 상단 새로고침 버튼으로 즉시 갱신 가능)
    • 차트는 최근 20개 샘플(약 5분 이력) 보존
    • 메모리 도넛 차트: 총 메모리 대비 사용량 (GiB 단위)
    hrSWRunTable을 제공하지 않는 장비(대부분의 L2 스위치 등)는 mock 데이터로 대체 표시됩니다. FortiGate, Linux 서버, 일부 라우터는 실제 지원합니다.
    hrSWRunPerfCPU는 누적 centiseconds 값이라 첫 폴링에는 이전 값이 없어 CPU%가 0%로 표시됩니다. 두 번째 폴링(15초 후)부터 정상 계산됩니다.

    9. 장애 예측¶

    선형회귀와 Z-score 이상 탐지로 CPU/메모리 추세를 분석하고 장애를 사전에 예측합니다. 좌측 리소스 트리(장비 유형별 그룹)에서 장비를 선택하면 중앙 워크스페이스에 아래 5개 탭이 로드됩니다.

    탭 기능 알고리즘
    Overview 예측 정확도(R²), 이상 탐지 건수, 예상 장애까지 시간 요약 + CPU 예측 차트 선형회귀
    Forecast CPU/Memory 7일 실측 + 12시간 예측선(점선) + 정상 범위 영역 + Warn/Crit 기준선 선형회귀 (최소제곱법)
    Anomaly 최근 24시간 raw 데이터 이상값 탐지, 상승/하강/안정 추세 표시 Z-score (|Z| > 2.5)
    Alert Tuning CPU/Memory Warning·Critical 임계값 슬라이더 조정 및 저장 —
    Analysis 메트릭별 기울기(slope), R², 추세, 위험도 요약 선형회귀

    예측 원리¶

    최근 20개 시계열 포인트로 최소제곱법 기울기·절편을 계산해 12시간 외삽(extrapolation)합니다. R²가 1에 가까울수록(0.7 이상 권장) 예측 신뢰도가 높고, 정상 범위는 ±1.5σ로 표시됩니다.

    이상 탐지 원리¶

    최근 24시간 평균(μ)·표준편차(σ)로 각 포인트의 Z값 = (값−μ)/σ를 계산, ±2.5 초과 시 이상값으로 판정합니다.

    우측 DataSource 패널에는 현재 수집 중인 모듈(CPU, Memory, Ping RTT, Interfaces) 활성 상태와 Root Cause 요약, Primary Signals가 표시됩니다.

    11. 알람 센터¶

    알람 상태 / 심각도¶

    상태 설명
    ACTIVE 임계치 초과 지속 중 또는 장비 DOWN
    ACKNOWLEDGED 담당자 인지 확인(여전히 활성) — 메트릭 정상화 시 자동 RESOLVED 전환
    RESOLVED 메트릭 정상 복귀 또는 장비 복구
    심각도 조건
    CRITICAL critical_value 이상, 또는 장비 DOWN(SNMP 무응답)
    WARNING warning_value 이상 ~ critical_value 미만

    임계치 적용 우선순위¶

    같은 메트릭에 여러 임계치가 정의될 수 있어, 다음 순서로 가장 구체적인 것 하나만 적용됩니다.

    1. 장비별 지정 임계치 (device_id 지정)
    2. 벤더+모델 임계치 (예: HP · DL580Gen9)
    3. 벤더 전용 임계치 (모델 미지정, 예: Fortigate 전체)
    4. 서버 유형 하드코딩 기본값 (device_type=server이고 위 1~3, 아래 5에 해당 없을 때만) — CPU 50% / 메모리 80% WARNING
    5. 전역(global) 임계치 — 벤더/장비 미지정

    임계치 설정은 알람 센터 → 임계치 설정 탭에서 관리합니다. 특정 장비를 지정하거나 비워두면 전체 장비(또는 전체 벤더)에 적용됩니다.

    장비별 CPU / 메모리 임계치¶

    알람 센터 → 임계치 설정 탭의 "장비별 CPU / 메모리 임계치" 표에서 장비 목록의 모든 장비를 벤더 · 모델 · 호스트명(IP) 단위로 보고, 장비마다 CPU·메모리의 경고/위험 값을 따로 지정할 수 있습니다.

    항목 동작
    입력칸의 회색 숫자 비워두면 적용되는 상속값(벤더+모델 → 벤더 → 전역 → 서버 기본 순)
    적용 기준 장비별 또는 상속 출처(벤더+모델/벤더/전역/서버 기본/없음)
    저장 입력한 값으로 장비별 임계치 생성·수정. CPU(또는 메모리)의 경고·위험을 둘 다 비우고 저장하면 그 지표는 장비별 설정이 삭제되어 상속값으로 돌아감
    ↺ 버튼 해당 장비의 장비별 임계치(CPU·메모리)를 모두 삭제하고 상속값으로 복귀
    활성 해제 장비별 값은 보관하되 알람 판정에는 상속값을 사용
    검색 / 필터 호스트명·IP·벤더·모델 검색, "장비별 설정된 장비만" 보기
    장비별 값은 지표 단위로 우선합니다. 예를 들어 CPU 경고만 장비별로 넣으면 그 장비의 CPU는 장비별 경고값만 사용하고(벤더 위험값은 쓰지 않음), 메모리는 계속 벤더/모델 값을 상속합니다. 경고 값은 위험 값보다 클 수 없고, 값 범위는 0~100%입니다.

    해결 (Resolve) 알람 행 선택 → [해결] 버튼

    이메일 알림 설정¶

    알람 센터 → 알림 설정 탭에서 수신자·발송 여부·반복 간격을 설정합니다.

    항목 설명
    알림 활성화 전체 이메일 발송 온/오프
    수신자 목록 세미콜론(;)으로 구분, 다중 입력 가능
    DOWN / CRITICAL / WARNING 알림 각각 독립적으로 켜고 끌 수 있음 (기본: DOWN·CRITICAL 켜짐, WARNING 꺼짐)
    반복 간격 DOWN/CRITICAL/WARNING마다 각각 분 단위로 설정 (기본 5/5/10분)
    이 화면에서는 SMTP 서버 자체(호스트·포트·계정·비밀번호·발신자)는 설정할 수 없습니다. SMTP는 SMTP_HOST/SMTP_PORT/SMTP_USER/SMTP_PASSWORD/SMTP_FROM 환경변수(docker-compose.yml 또는 .env)로만 설정하며, 바꾸면 백엔드 컨테이너 재시작이 필요합니다.

    발송 정책 — 장비 DOWN/UP

    상황 동작
    앱 시작 시 이미 DOWN 메일 미발송
    UP → DOWN 전환 즉시 1회 발송
    DOWN 지속 설정한 간격(기본 5분)마다 반복 발송
    DOWN → UP 전환 복구 메일 1회 발송
    앱 시작 시 이미 UP 메일 미발송

    발송 정책 — 임계치 CRITICAL/WARNING

    DOWN/UP과 별개로, CPU·메모리 등 임계치 초과로 알람이 발생하면 해당 심각도의 알림이 켜져 있을 때 설정한 간격(기본 CRITICAL 5분·WARNING 10분)마다 반복 발송됩니다. 메트릭이 정상 복귀해 알람이 RESOLVED되면 반복 발송이 멈춥니다.

    [테스트 발송] 버튼으로 SMTP 연결을 검증할 수 있습니다. 시각은 모두 KST(UTC+9), YYYY/MM/DD HH:MM:SS 형식입니다.

    12. MIB Browser¶

    등록된 장비를 대상으로 SNMP Walk/GET을 수동 실행하고 OID 값을 조회합니다.

    기본 사용법¶

    1. 대상 장비 선택 (IP 직접 입력 또는 등록 장비 목록에서 선택)
    2. OID 입력 (예: 1.3.6.1.2.1.1)
    3. SNMP Walk 또는 GET 선택 후 조회
    4. 결과 테이블에서 OID, 값, 타입 확인

    MIB 파일 로드¶

    [Load MIB] 버튼으로 .mib/.txt/.my 파일을 로드하면 좌측에 OID 트리가 표시됩니다. 화살표(▶/▼)로 하위 노드 펼침/접기, 기본 2단계까지 자동 펼침, 검색창으로 이름 필터링 가능.

    SNMP 진단 (snmp-diag)¶

    장비의 SNMP 응답 여부와 지원 OID를 한 번에 확인합니다. 벤더별 전용 OID(FortiGate, Juniper, Handreamnet, NetScreen 등)도 자동 테스트합니다.

    SNMP 진단은 대상 장비에 다수의 SNMP 요청을 발송합니다. 폴링 중 실행 시 장비 부하에 주의하십시오.

    13. SNMP 설정 가이드 (장비 측)¶

    Cisco IOS / IOS-XE¶

    snmp-server community public RO
snmp-server location HQ-Server-Room
snmp-server contact admin@company.com

    Cisco NX-OS¶

    snmp-server community public group network-operator
feature snmp

    FortiGate¶

    config system snmp community
  edit 1
    set name public
    config hosts
      edit 1
        set ip <NMS-IP>/32
      end
    end
  next
end
config system snmp sysinfo
  set status enable
end

    Juniper Junos (SRX/EX/MX 등)¶

    set snmp community public authorization read-only
set snmp location "HQ-Server-Room"
set snmp contact "admin@company.com"

    Juniper SSG / ScreenOS (NetScreen)¶

    set snmp community public Read-Only
set snmp host <NMS-IP>
set snmp port 161

    TP-Link (TL-SG2xxx / T2600G)¶

    Web UI: Management > SNMP > SNMP Config → Community Name: public, Access: Read-Only

    Handrim (한드림넷) SG2024GPOE¶

    Web UI: 시스템 > SNMP 설정 → Community: public, 권한: 읽기전용, Trap 수신 IP: NMS 서버 IP

    14. 폴링 엔진 구조¶

    PollerEngine (60초 주기, POLL_INTERVAL)
  └── 매 사이클 시작 시 metrics_raw 파티션 존재 여부 확인 (자동 생성)
  └── 장비별 SNMPWorker (병렬, 최대 20 동시 — POLLER_WORKERS)
        ├── Ping (ICMP 4회)
        ├── _collect_system    → sysDescr, sysName, sysUptime ...
        ├── _collect_cpu       → 아래 CPU 전략 순서 참고
        ├── _collect_memory    → 아래 메모리 전략 순서 참고
        ├── _collect_interfaces → IF-MIB + IF-MIB HC (64bit 카운터)
        ├── _collect_proto_stats → ICMP/TCP/UDP 카운터
        └── _collect_disks     → HR-MIB hrStorageTable (고정 디스크)

  DB 저장 순서:
    1. sync_interfaces()        → device_interfaces 테이블 upsert
    2. _persist()                → metrics_raw 테이블 insert
    3. _update_device_status()   → devices.status 갱신
    4. _upsert_sys_state()       → device_sys_state upsert
    5. commit()

    CPU 수집 전략 순서¶

    1. 벤더 자동 감지 우선 시도 — sysDescr/sysObjectID로 FortiGate·Juniper(Junos)·Juniper SSG(ScreenOS)를 식별하면 해당 벤더 전용 OID(fgSysCpuUsage, jnxOperatingCPU, nsResCpuLast1Min)를 가장 먼저 시도. 여기서 값을 얻으면 즉시 사용하고 아래 단계는 건너뜀
    2. HR-MIB hrProcessorLoad (RFC 2790, 서버/Linux) 2~3. UCD-SNMP ssCpuIdle / ssCpuUser+ssCpuSystem (Linux/OpenWRT/pfSense)
    3. Cisco PROCESS-MIB / OLD-CISCO-CPU-MIB (여러 세대 OID 순차 시도) 5~9. TP-Link, H3C, Huawei, Zyxel, Mikrotik 전용 OID 10~13. Juniper, FortiGate, Handreamnet, NetScreen 전용 OID (0번에서 감지되지 않았거나 실패한 경우의 폴백)

    메모리 수집 전략 순서¶

    1. 벤더 자동 감지 우선 시도 — CPU와 동일한 방식으로 fgSysMemUsage, jnxOperatingHeap, nsResMemAlc/Left를 우선 시도
    2. UCD-SNMP memAvailReal + memBuffer + memCached (Linux) — 캐시/버퍼를 회수 가능한 메모리로 명시적으로 더해 계산 (free -m 방식과 동일). Net-SNMP 구버전에서 memAvailReal이 순수 free만 반환하는 경우까지 커버하기 위함
    3. HR-MIB hrStorageRam — Linux에서는 캐시를 반영하지 않아 실제보다 부풀려질 수 있어 UCD-SNMP보다 후순위
    4. Cisco MEMORY-POOL-MIB / ENHANCED-MEMPOOL-MIB 4~5. TP-Link, H3C 전용 OID 6~8. FortiGate, Handreamnet, NetScreen 전용 OID (0번 폴백)
    지원하지 않는 장비는 CPU/메모리가 "수집 불가"로 표시됩니다. 어떤 MIB이 실제로 응답하는지는 MIB Browser의 SNMP 진단 또는 백엔드 로그(grep -E "CPU\[|Mem\[")로 확인할 수 있습니다.

    수집 메트릭 ID 참고표¶

    메트릭 ID 설명 단위
    cpu_util CPU 사용률 %
    mem_util 메모리 사용률 %
    ping_rtt Ping 평균 응답시간 ms
    ping_loss Ping 패킷 손실률 %
    if_in_octets / if_out_octets 인터페이스 수신/송신 트래픽 bps
    if_in_errors / if_out_errors 수신/송신 에러 카운트 count

    직접 DB 접속 (진단용)¶

    PGPASSWORD=zenith psql -h localhost -U zenith -d zenithnms

    주요 진단 쿼리: 

    -- 장비별 인터페이스 수
SELECT d.hostname, COUNT(di.id) as iface_count
FROM devices d
LEFT JOIN device_interfaces di ON di.device_id = d.id
GROUP BY d.id, d.hostname;

-- 최근 1시간 메트릭 수
SELECT metric_type, COUNT(*) FROM metrics_raw
WHERE time > NOW() - INTERVAL '1 hour'
GROUP BY metric_type;

-- 활성 알람
SELECT * FROM alert_events WHERE status = 'active' ORDER BY triggered_at DESC;

-- 벤더/모델별 임계치 확인
SELECT id, device_id, metric_type, vendor, model, warning_value, critical_value
FROM alert_thresholds ORDER BY id;

    16. 장애 진단¶

    인터페이스 탭에 데이터 없음¶

    sudo docker compose logs backend | grep -E "IF-MIB|sync_interfaces|bulkwalk"
    SNMP 진단(MIB Browser → snmp-diag)에서 빈 결과면 장비 SNMP 설정 또는 방화벽 문제.

    CPU/메모리 표시 안 됨 또는 값이 이상함¶

    1. 로그에서 실제로 어떤 전략이 잡혔는지 확인: 
      sudo docker compose logs backend | grep -E "CPU\[|Mem\["
      Mem[HR-MIB]처럼 특정 전략 태그가 찍힙니다. 벤더 전용 전략이면 Mem[FortiGate/vendor-detected]처럼 /vendor-detected 접미사가 붙습니다.
    2. 앱 자체 GUI(있는 경우) 값과 비교해서 다르면, 해당 장비가 어떤 MIB을 실제로 지원하는지 SNMP 진단으로 재확인
    3. 필요 시 원본 OID 값을 직접 조회해 어떤 계산식이 실제 값과 맞는지 검증 후 backend/app/poller/snmp_worker.py에 전략 추가/우선순위 조정

    장비 status = down인데 실제로는 살아있음¶

    ping <장비IP>
snmpwalk -v2c -c public <장비IP> 1.3.6.1.2.1.1.1.0
    SNMP Community/포트 설정을 확인하십시오.

    폴링이 전혀 안 됨¶

    sudo docker compose logs backend | grep "Poller"
    Poller engine started 메시지가 없으면 pysnmp 임포트 오류입니다.

    sudo docker compose logs backend | grep -E "ERROR|WARNING" | head -20

    17. 모바일 접속 (WSL2)¶

    1단계 — WSL IP 확인¶

    PowerShell: 

    wsl hostname -I
    → 172.x.x.x 확인

    2단계 — 포트포워딩 (관리자 권한 PowerShell)¶

    netsh interface portproxy add v4tov4 listenport=3000 listenaddress=0.0.0.0 connectport=3000 connectaddress=172.x.x.x

    3단계 — 방화벽 허용¶

    New-NetFirewallRule -DisplayName "ZenithNMS" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow

    4단계 — 모바일 접속¶

    http://<PC의-IPv4-주소>:3000

    WSL2 재시작 시 내부 IP가 변경되므로 포트포워딩 재설정 필요. 참고로 ~/projects/tunnel.sh로 외부 접속용 터널을 띄울 수 있습니다.
