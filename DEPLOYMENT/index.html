    ZenithNMS — 배포 가이드¶

    Docker Compose 기반 단일 호스트 배포입니다. 별도의 오케스트레이션(K8s 등)이나 CI/CD 파이프라인은 없고, 서버(또는 WSL2)에서 직접 docker compose로 빌드/기동합니다.

    1. 사전 요구사항¶

    • Docker, Docker Compose 플러그인
    • 프로젝트 루트에 .env, auth.env 파일 (git에 포함되지 않음 — 자세한 항목은 README.md의 "환경변수 설정" 참고)

    2. 최초 배포 (신규 설치)¶

    git clone <repo> zenithnms
cd zenithnms

# .env, auth.env 생성 — README.md "환경변수 설정" 참고
# 특히 auth.env의 AUTH_USER_* 3종을 설정하지 않으면 로그인 자체가 불가능함

sudo docker compose up -d --build
    • postgres 컨테이너가 처음 뜰 때(볼륨 pg_data가 비어있을 때) backend/migrations/init.sql이 docker-entrypoint-initdb.d를 통해 자동 실행되어 전체 스키마(테이블 + 초기 파티션)가 생성됩니다.
    • backend는 postgres의 healthcheck 통과 후 기동되고(depends_on: condition: service_healthy), 자체 healthcheck(GET /api/health)를 통과해야 frontend가 기동됩니다.
    • 접속: http://localhost:3000

    3. 배포 업데이트 (기존 운영 환경에 새 버전 반영)¶

    cd ~/projects/zenithnms
git pull                          # 또는 원하는 브랜치/태그로 checkout
sudo docker compose up -d --build # 변경된 서비스만 이미지 재빌드 후 재기동
    • 무중단 배포가 아닙니다. backend/frontend 컨테이너가 재생성되는 동안 짧은 다운타임이 발생합니다. postgres는 이미지가 안 바뀌면 재생성되지 않습니다.
    • docs/ 폴더는 읽기 전용 볼륨으로 마운트되어 있어(./docs:/app/docs:ro), docs/manual.md·docs/api-reference.md 등 문서만 수정한 경우 재빌드 없이 즉시 반영됩니다.
    • ⚠️ 프론트엔드는 docker compose up -d --build frontend만으로는 반영되지 않습니다. docker-compose.yml이 ./frontend/dist:/usr/share/nginx/html:ro로 호스트의 frontend/dist 폴더를 그대로 마운트하고 있어서, Dockerfile 안에서 이미지를 새로 빌드해도 nginx는 계속 호스트의 기존 dist 내용을 서빙합니다. 프론트엔드 소스를 고쳤다면 반드시 호스트에서 직접 빌드하세요: 
      cd ~/projects/zenithnms/frontend
npm run build
      dist가 갱신되면 볼륨을 통해 즉시 반영되며, 컨테이너 재시작조차 필요 없습니다(브라우저 새로고침만 하면 됨). 반대로 docker compose up -d --build frontend만 실행하고 이 단계를 빠뜨리면, 백엔드 API 변경(예: 인증 요구사항 추가)과 프론트엔드 코드가 맞지 않아 화면이 깨지는 채로 배포될 수 있습니다 — 실제로 2026-09-01 API 인증 적용 배포 때 이 문제로 대시보드/장비 목록이 전부 401로 실패한 적이 있습니다.

    4. DB 스키마 마이그레이션¶

    ⚠️ 마이그레이션 이력을 추적하는 도구(Alembic 등)가 없습니다. backend/migrations/에는 3개 파일이 있습니다.

    파일 용도
    init.sql 신규 설치 시 자동 실행되는 현재 기준 전체 스키마 (파티션 테이블·alert_thresholds의 vendor/model 컬럼 등 이미 반영된 최신본)
    add_partitions.sql 과거에 이미 떠 있던 운영 DB에 파티션 구조를 추가했던 1회성 마이그레이션 기록
    add_threshold_vendor_model.sql 과거에 alert_thresholds에 vendor/model 컬럼을 추가했던 1회성 마이그레이션 기록

    즉 신규 설치는 init.sql만으로 충분하고, 뒤의 두 파일은 이미 반영된 과거 이력입니다. 앞으로 스키마를 바꿀 때는:

    1. init.sql을 최신 스키마로 갱신 (신규 설치 기준)
    2. 기존에 떠 있는 운영 DB에는 변경분만 담은 새 SQL 파일을 backend/migrations/에 추가하고, 아래처럼 수동 적용
    sudo docker compose exec -T postgres psql -U zenith -d zenithnms -v ON_ERROR_STOP=1 --single-transaction < backend/migrations/새파일.sql

    -v ON_ERROR_STOP=1 --single-transaction을 빼면 중간에 에러가 나도 psql이 계속 진행해 스키마가 일부만 바뀐 채 정상 종료된 것처럼 보일 수 있습니다. 반드시 위 옵션과 함께 실행하세요.

    적용 여부를 추적하는 테이블이 없으므로, 어떤 마이그레이션을 어떤 환경에 적용했는지는 파일명·날짜와 이 문서(또는 CHANGELOG.md)에 직접 기록해 관리해야 합니다.

    5. 롤백¶

    • 코드만 롤백: git checkout <이전 커밋/태그> 후 sudo docker compose up -d --build. ⚠️ 3. 배포 업데이트에서 설명한 것과 동일한 이유로, 프론트엔드가 바뀐 롤백이라면 cd frontend && npm run build도 반드시 함께 실행해야 합니다 — 안 하면 git checkout으로 코드는 되돌렸는데 화면(frontend/dist)은 이전 버전 그대로라 롤백이 안 된 것처럼 보입니다.
    • 스키마 변경이 있었던 배포를 롤백할 경우: 코드 롤백만으로는 부족합니다. 새 컬럼/테이블이 이전 코드와 호환되는지 확인하고, 호환 안 되면 DB도 백업본에서 복구해야 합니다 (아래 RUNBOOK.md의 백업/복구 참고). 사전 백업 없이 스키마 변경을 배포하지 마세요.

    6. 외부 접속¶

    내부망 밖에서 접속해야 하면 프로젝트 공통 터널 스크립트를 사용합니다.

    bash ~/projects/tunnel.sh

    localtunnel로 3000번 포트를 임시 공개 URL로 노출합니다 (PC/서버가 켜져 있는 동안만 유효, 인증 없이 인터넷에 노출되므로 발급된 URL을 필요한 사람에게만 공유).
